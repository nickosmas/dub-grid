# Supabase Agent Instructions

Scope: `supabase/`.

Local Supabase configuration, canonical migrations plus numbered forward
migrations, seed SQL, and compiled auth email templates.

## Verified Structure

```
supabase/
  config.toml                     # Local Supabase config; custom_access_token hook enabled
  migrations/
    001_schema.sql                # Enums, tables, FKs, indexes, realtime
    002_functions_triggers.sql    # Functions, triggers, RPCs, JWT hook implementation
    003_rls_policies.sql          # RLS ENABLE + all row-level security policies
    004_grants.sql                # Grants + default privileges + supabase_auth_admin grants
    005_*.sql ...                 # Ordered, idempotent forward migrations
  seed_arden_wood.sql             # Local seed: Arden Wood org
  seed_calm_haven.sql             # Local seed: Calm Haven org
  seed_gridmaster.sql             # Local seed: gridmaster user
  snippets/                       # SQL utility snippets (not migrations)
  templates/                      # Compiled HTML auth emails (generated by email:build)
    confirmation.html  email_change.html  invite.html
    magic_link.html    reauthentication.html  recovery.html
```

## Migration Rules (CRITICAL)

- Keep the first four migrations as the canonical clean-install definition:
  - `001_schema.sql` — enums, tables, foreign keys, indexes, realtime publication
  - `002_functions_triggers.sql` — functions, triggers, RPCs, JWT hook logic
  - `003_rls_policies.sql` — `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + all policies
  - `004_grants.sql` — grants to `anon`, `authenticated`, `service_role`,
    `supabase_auth_admin`, and default privileges
- Existing databases receive changes through ordered, idempotent forward
  migrations (`005_...sql` and later). Keep the canonical files synchronized
  so clean installs and upgraded databases converge.

## config.toml: JWT Hook (CRITICAL)

The `custom_access_token_hook` must be enabled for local dev:

```toml
[auth.hook.custom_access_token]
enabled = true
uri = "pg-functions://postgres/public/custom_access_token_hook"
```

Without this, the JWT hook does not run locally and JWT claims (`org_role`,
`org_id`, `platform_role`, etc.) are absent from access tokens.

## supabase_auth_admin Grants (CRITICAL)

Any table the `custom_access_token_hook` reads MUST have explicit grants in
`004_grants.sql` for `supabase_auth_admin`. Currently granted:

```sql
GRANT USAGE ON SCHEMA public TO supabase_auth_admin;
GRANT SELECT ON TABLE public.profiles TO supabase_auth_admin;
GRANT SELECT ON TABLE public.organization_memberships TO supabase_auth_admin;
GRANT SELECT ON TABLE public.organizations TO supabase_auth_admin;
GRANT SELECT, INSERT ON TABLE public.user_sessions TO supabase_auth_admin;
GRANT SELECT, DELETE ON TABLE public.jwt_refresh_locks TO supabase_auth_admin;
```

If a new table is added to the hook logic in `002_functions_triggers.sql`,
add its grant in `004_grants.sql` immediately. Testing via direct SQL is NOT
sufficient — verify via `signInWithPassword` to confirm the hook can read the
table under the auth role.

## Post-DROP/CREATE Schema Grants (CRITICAL)

After `DROP SCHEMA public CASCADE; CREATE SCHEMA public` (used in remote reset),
`ALTER DEFAULT PRIVILEGES` alone does not grant on existing objects — it only
applies to future ones. `004_grants.sql` must explicitly call:

```sql
GRANT ALL ON ALL TABLES IN SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL FUNCTIONS IN SCHEMA public TO anon, authenticated, service_role;
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO anon, authenticated, service_role;
```

Without this, all queries fail silently and auth/RBAC/subdomain routing breaks.

## JWT Claims Structure

The `custom_access_token_hook` writes claims at the **top level** of the JWT
payload (not inside `app_metadata`):

- `platform_role`, `org_role`, `org_id`, `org_slug`

The Next.js request proxy (`apps/web/src/proxy.ts`) reads these via `jwtVerify`
/ `decodeJwt` at the top level.

## Key Tables

- `profiles` — `id`, `org_id`, `platform_role`, `version`, `role_locked`, `mfa_enabled`, `last_sign_in_at`
- `organizations` — org data, `suspended_at`, `archived_at`, `workspace_kind`, `feature_overrides` (JSONB), Stripe fields, trial fields
- `organization_memberships` — per-org role + `admin_permissions` (JSONB, 25 permissions) + `department_ids[]` + `archived_at`
- `departments` — `type` (`scheduled|management`), `permissions` (JSONB, vestigial), `abbr`
- `organization_roles` — configurable display roles + `department_id`
- `employees` — `status`, `user_id` (nullable FK), `department_ids[]`, `focus_area_ids[]`
- `user_sessions` — per-device session tracking; `active_org_id` drives JWT claims per session
- `shifts` — `org_id` NOT NULL, optimistic locking, custom time format validation
- `recurring_shifts` — per-employee recurring shift templates
- `shift_requests` — pickup/swap/calloff with approval workflow
- `notifications` — in-app/email with org-scoped constraint
- `jwt_refresh_locks` — blocks JWT refresh for 5s after role change
- `invitations` — invite-only registration, 72-hour expiry, `employee_id` FK
- `role_change_log` — immutable audit trail with `idempotency_key UNIQUE`
- `impersonation_sessions` — gridmaster impersonation, 30-min expiry
- `schedule_draft_sessions` — cell locks for concurrent editing
- `publish_history` — schedule publish audit trail with JSONB changes

## Database and RLS Rules

- Treat schema, RLS, grants, auth hooks, storage, and seed data as high risk.
- Never weaken RLS policies, grants, `org_id` filters, membership checks, or
  `auth.uid()` checks without explicit approval.
- Preserve tenant isolation for all organization-owned data.
- Do not write destructive SQL (`DROP`, `TRUNCATE`, broad `DELETE`, broad `UPDATE`)
  unless explicitly requested and rollback is documented.
- Never use service-role keys in client-side or mobile code.

## Seed Data

- `seed_arden_wood.sql`, `seed_calm_haven.sql`, `seed_gridmaster.sql` are local-only.
- They are NOT run on production. The remote reset script (`scripts/reset-remote-db.ts`)
  runs every numbered migration in lexical order, then a separate seed path.

## Verification

- Inspect the canonical files and relevant forward migrations before editing.
- For schema/RLS changes, run `npm run db:reset` locally when possible (resets local DB).
- Run `npm run gen:types` when schema changes affect generated types (`apps/web/src/lib/database.types.ts`).
- Do not run `npm run db:reset:remote` unless the user explicitly requests it and
  confirms the destructive remote risk.
- Both remote scripts connect through `scripts/lib/db-client.ts`. Networks that
  filter database ports (5432/6543) fail the direct connection with ECONNRESET or
  a connect timeout, and Supabase's direct host is IPv6-only, so the client falls
  back to running the same SQL over HTTPS via the Supabase Management API when
  `SUPABASE_ACCESS_TOKEN` (or a `supabase login` token) is available. Pin one
  transport with `SUPABASE_DB_TRANSPORT=postgres|https`.
